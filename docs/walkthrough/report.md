## 结论三问

1. **链路逻辑通顺吗？** 主流程通顺（17 条中 13 条走通），但"失败分支"和"状态归属"系统性薄弱。
2. **是补丁叠补丁吗？** **是。** 最典型是任务注册 6 入口（P-01/P-02/P-04）、屏幕状态 5 源（P-03/P-06/P-07）、配置反向恢复（P-13）。每次只补出事的那条路径。
3. **会无法操作/出 bug 吗？** 会。P-02 会导致"关了定时还继续熄屏"，P-01/P-03 会导致状态显示与事实相反。

## 根因诊断（回答用户"修不到真正的地方"）

**根因：没有"单一事实源"（SSOT）+ 写入路径发散。**

| 职责 | 应该的归属 | 实际的写入者 | 后果 |
|---|---|---|---|
| 定时 enabled 状态 | `save_schedule`/`cancel_schedule` 单一入口 + 失败统一回滚 | 6 个入口各自 `save_config` + 4 种失败处理 | P-01/P-02/P-04 |
| 屏幕亮灭状态 | `screen_verdict` 单一判定 + `mark_screen_state` 单一落盘 | 磁盘账 + 拓扑 ACTIVE + DDC 回读 + 内存账 4 套 | P-03/P-06/P-07 |
| 档位判定 | `active_slot_dict` 单一实现 | `active_slot` 与 `active_slot_dict` 两套 | P-09（潜在） |
| 任务注册 | `ensure_task_registration` 单一入口（含自愈比对） | 3 处直接 `register_tasks` 绕过 | P-04 |

**之前几次修复为什么像打补丁**：`_finish_apply` 重名、接回亮度漏写、断开屏不显示——每次都是"某条路径的某个回调/参数错了"，改的是**那条路径**；但产生这些错误的共同原因是**同一职责被复制到多条路径**，每条各自演化、各自补。只改出事那条，下一条迟早再犯。

# 用户纠偏：剩余 4 项的共同前提是错的（v2.01.0）

用户看完第 2 轮报告后给出关键纠正（原文）：

> "拓扑就是可以被修改的，这个软件的职责只是读取当前状态和调整当前状态。它不需要维护任何状态。
> 定时任务的话是可以在指定时间调整到指定状态的。所以你现在的 2、3、4，我感觉都是第一个问题的
> 衍生问题呢。你对于这个程序的功能以及它的作用，你的理解都有点偏。"

**他没说哪一项该修，而是指出这 4 项同源**：它们都以"程序要记住点什么"为前提。
前提一撤，4 项一起消失：

| 编号 | 原问题（以"程序维护状态"为前提） | 前提撤掉后的结论 |
|---|---|---|
| E1-06 拓扑快照过期 | 快照无 TTL，用户改拓扑后被旧快照覆盖 | 快照**根本不该被当作状态**。接回改为现读当前拓扑 + 现算 mode，历史快照不再参与接回，只在本次操作失败时用于内存回滚 → 问题消失 |
| E1-07 `load_config` 读中写盘 | GUI 内存旧、磁盘新，整文件覆盖回退 | 不记运行态 → 无需跨进程合并 → 问题消失 |
| E2-04 `--force` 被 disabled 吞掉 | 显式指令被"记住的开关"挡住 | 改为"force = 强制对齐"，两个方向都做（启用重建 / 未启用清残留） |
| E2-05 `ddc_allow_undeclared` 单向阀门 | 一次同意永久生效，换屏后风险被继承 | 它是"本次危险动作的授权"而非状态，离开 ddc 方式即收回 |

## 落地

- 删除 `screen_state` / `screen_state_at` / `screen_off_tick` 与全部读写点（详见 CHANGELOG v2.01.0）。
- 拓扑接回改为 `topology_plan_on()`（纯函数）+ `_ccd_apply_plan_on()`（就地写 path）：
  现算 `sourceInfo.modeInfoIdx = (srcMode<<16)|0xFFFF`、
  `targetInfo.modeInfoIdx = (tgtMode<<16)|desktopMode`；
  **真机实测**（`scripts/topo-declarative-probe.py --verify`）与 Windows 自己填的值逐位一致。
- 非拓扑模式下状态卡不再给亮灭断言（读不到就说不知道），只有一个可信方向被采用：
  `0xD6` 报 2/3/4/5 才算灭。

## 这一轮的方法论教训（写进坑库）

**判断"这是不是状态账"的三个问句**：

1. 这个字段存的是"系统的当前事实"，还是"我上次做了什么"？
   —— 存"我上次做了什么"的，一律不能拿来回答"现在是什么"。
2. 如果用户在我不知道的情况下改过系统，我还对不对？
   —— 会对不上，就说明我在替他维护状态。
3. 删掉这个字段，功能会不会真的坏？
   —— 常常不会：真正需要的是"每次现读"，而现读往往比记账更准（拓扑 ACTIVE 就是例子）。

教训：**"两个来源不一致怎么办"这类问题的正确解法，通常不是加合并/加 TTL/加优先级，
而是问"为什么会有两个来源"**。这一轮的 4 项全部属于"问题本身不该存在"。

## 风险提示（经查证修正，原说法说反了）

原写"默认 topology 与镜像式远控冲突、可能黑屏；DDC 不受影响"——**错误**，

| 来源 | 关键事实 |
|---|---|
| 微软 DXGI `DuplicateOutput` 文档 | 桌面复制是 **per-output**；显示器增删/模式变化使 duplication 失效需重建 |
| Sunshine `output_name` 文档 | 可写死 `\\.\DISPLAY1`，但**默认选"默认显示器"** |
| Sunshine issue #5673、24H2DummyFix | **Win 11 24H2 起，"当前选中的显示器"离线/断电 → DXGI 整体初始化失败** |
| ToDesk 官方帮助中心「虚拟屏」 | 虚拟屏开启后"原显示器会显示黑屏"，远程正常；可"直接关掉物理显示器，只靠虚拟屏运行" |

被断开的物理屏才会失败。DDC 待机在深度睡眠面板上反而可能触发 24H2 的
DXGI 回归。**默认 topology 保证"总有一块在线屏"，确定性最高。**
