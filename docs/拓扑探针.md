# 显示器拓扑只读探针

> 回到 [README](../README.md) · [文档索引](index.md)

脚本：[`scripts/topology_probe.py`](../scripts/topology_probe.py)。
**只读**：只调 `QueryDisplayConfig` / `EnumDisplayDevices` / `EnumDisplayMonitors` /
`GetVCPFeatureAndVCPFeatureReply`，不写任何显示设置（无 `SetDisplayConfig`）。

## 用途

给"拓扑断开/接回"方案做**实证基线**，回答三个问题：

1. Windows 看到的屏和程序看到的屏是不是同一批？
2. 用什么字段当稳定锚点？`DISPLAYn` 到底靠不靠谱？
3. 虚拟屏能不能单独识别？断开态下 DDC 是不是真的读不到？

## 怎么跑

```bash
python scripts/topology_probe.py                 # 人读表格（约 1 秒）
python scripts/topology_probe.py --no-ddc        # 跳过 DDC 读取
python scripts/topology_probe.py --json          # 机器可读，含全部原始 path
python scripts/topology_probe.py --all-paths     # 额外展开全部原始 path
python scripts/topology_probe.py --out baseline.txt
```

无第三方依赖；Windows 10/11 + Python 3.10+ 均可。
结构体尺寸会打印在开头，用于跨机器核对 ctypes 布局是否对齐
（本机实测 `PATH_INFO=72` / `MODE_INFO=64` / `TARGET_DEVICE_NAME=420`）。

## 字段口径

| 字段 | 含义 |
|---|---|
| `ACTIVE` | `path.flags & 0x1`：Windows 正在这条 path 上输出 |
| `targetAvailable` | 1 = 设备仍连接（**被禁用也还是 1**）；0 = 真断开/拔线 |
| 稳定锚点 | 显卡 LUID + EDID 厂商/产品码 + `connectorInstance` |
| 虚拟屏 | friendly name 含 VDD/Virtual/IddCx |

## 2026-11-27 实测结论（脱敏）

原始输出存于工作区 `topology-baseline-2026-11-27.txt`（含硬件路径，不入库）。

| 观察 | 数字 / 事实 |
|---|---|
| `QDC_ALL_PATHS` 的 path 数 | **233** 条，但只有 **3 块屏**（2 物理 + 1 VDD）；224 条是未连接的 source×target 组合 → 必须折叠，不能按 path 当屏 |
| `DISPLAYn` 是否唯一 | ❌ **不唯一**：同一块物理屏对应 `DISPLAY1/2/3/4` 四个 source，ACTIVE 的那个才是当前桌面视图 |
| 两块同型号屏如何区分 | EDID `mfr/prod` 相同，但 `connectorInstance` 分别为 1 / 2 → **稳定锚点唯一** |
| 虚拟屏 | `VDD by MTT`，inactive 但 `targetAvailable=1`，锚点独立 → 可以从物理屏里排除 |
| DDC 可及性 | 只有 ACTIVE 的屏能读到 `0x10=43/100`、`0xD6=1`；inactive 的 VDD 读不到 |
| `EnumDisplayMonitors` | 只有 2 条（对应 ACTIVE 的 physical 屏），拿不到 VDD |

**对设计的直接影响**：`monitor_ids` 存 `DISPLAYn` 的方案必须换掉；
"屏"的粒度只能由稳定锚点定义，`DISPLAYn` 只作为 CCD source → GDI 视图的临时映射。

## C2/C3/C4 实测（2026-11-27，真机，两屏交替、任一时刻最多灭一块）

脚本：[`scripts/topology_switch.py`](../scripts/topology_switch.py)；
默认 dry-run，必须 `--apply` 才提交；动作前存原始字节快照（仓库外），失败自动回滚。

| 实验 | 结果 |
|---|---|
| 断开副屏（`connectorInstance=2`） | `SetDisplayConfig` rc=0；**全程 805ms**（含 Python 启动）；回读确认 `ACTIVE=0` 且 `targetAvailable=1` |
| 接回副屏 | 恢复快照后回读 `ACTIVE=1`；DDC 恢复可读；**全程 986ms**（含 Python 启动） |
| 断开主屏（`connectorInstance=1`） | ❌ **rc=87 `ERROR_INVALID_PARAMETER`** —— Windows 不允许直接把主屏从拓扑移除；状态未被改动。护栏已加：脚本识别主屏并直接拒绝 |
| 计划任务内查询 CCD | 临时任务（`LogonType=Interactive`、当前用户）触发成功：`rc=0 pathCount=233 active=2 user=2504` → **计划任务里 CCD 查询可用**；任务已清理 |
| dry-run / 快照 | dry-run 未改任何状态；快照按原始 ctypes 字节保存，`--on` 原样恢复成功 |

**设计结论**：有界轮询上限取 2 秒足够（实测含进程启动都在 1 秒内）；
主屏禁止作为断开目标，除非先做"换主屏 + 断开"的两步事务（本次不做）。

## 持久化与窗口副作用实测（2026-11-27）

用 `scripts/topology_side_probe.py` 在 off 前 / off 中 / 接回后各采一次：

| 项 | 结果 |
|---|---|
| `QDC_DATABASE_CURRENT` | 断开前 `topologyId=4, active=2/2`；断开中 **`topologyId=1, active=1/1`**；接回后恢复 `4 / 2/2` → **`SDC_SAVE_TO_DATABASE` 确实把断开态写进了 CCD 数据库**，不用重启也能确认持久化 |
| 窗口位置 | off 时 **3 个窗口被移动**（WorkBuddy、AE 主窗、AE 子窗都从副屏被挤到主屏）；6 个窗口消失（被最小化/隐藏） |
| 接回后 | 19 个可比窗口中 **17 个回到原位**，2 个未恢复（AE 子窗、Program Manager）；6 个消失的窗口有 5 个回来 → **Windows 会尽量恢复，但不保证** |

**对设计的含义**：文档必须写清"断开会让该屏上的窗口迁移，接回后大部分会回来但不是全部"；
不要把它当作无副作用操作。可用 Windows 自带「断开显示器时最小化窗口」开关减轻影响，
但那属于用户系统设置，程序不改。

## 声明式接回的实证（2026-11-27，v2.01.0）

脚本：[`scripts/topology_declarative_probe.py`](../scripts/topology_declarative_probe.py)（默认只读）
+ [`scripts/topology_live_check.py`](../scripts/topology_live_check.py)（真跑，需 `--yes`）。

**要回答的问题**：接回能不能不依赖"断开前存下的整份快照"？
如果不能，那"用户在断开期间改了 Windows 显示设置、接回时被旧快照覆盖"就无解。

### 关键发现：modeInfoIdx 可以从当前 modes 数组现算

`DISPLAYCONFIG_PATH_*_INFO.modeInfoIdx` 是位域，不是普通下标：

| 字段 | 位布局 |
|---|---|
| `sourceInfo.modeInfoIdx` | 低 16 位 `cloneGroupId`（无克隆组时为 `0xFFFF`）／高 16 位 `sourceModeInfoIdx` |
| `targetInfo.modeInfoIdx` | 低 16 位 `desktopModeInfoIdx`／高 16 位 `targetModeInfoIdx` |

所以只要知道"这块屏的 source id 和 target id"，就能在**当前** modes 数组里按
`(infoType, id)` 查出三个下标（infoType：1=SOURCE、2=TARGET、3=DESKTOP_IMAGE）。

`--verify` 的只读自检结果（本机）：

```
path#0  AE30/68C7/1  src 算=0x0001FFFF 实=0x0001FFFF OK | tgt 算=0x00000002 实=0x00000002 OK
path#1  AE30/68C7/2  src 算=0x0004FFFF 实=0x0004FFFF OK | tgt 算=0x00030005 实=0x00030005 OK
→ 全部一致 → 接回可完全现算，不需要历史快照
```

### 另一个细节：source id 是 adapter 内的独占资源

`QDC_ALL_PATHS` 里同一块屏会有多条 path（本机每块物理屏 4 条）。把某条 path 置
`ACTIVE` 时，它的 `sourceInfo.id` 必须**没被其它 ACTIVE path 占用**，否则
`SetDisplayConfig` 直接失败。所以接回时按"未被占用 + id 最小"挑，是确定性的、
与"上次用的是哪条"无关。

### 产品里的落点

- `topology_plan_on(anchors, rows, mode_entries)`：纯函数，给出要动哪几条 path、填哪三个下标；
- `_ccd_apply_plan_on(paths, plan)`：就地写进 `paths`（`flags |= ACTIVE` + 两个位域）；
- `topology_on(anchors)`：现读 → 计划 → 提交 → 回读；现算的三元组被拒时，
  退到"source 现算 + target/desktop 交 Windows"（见下一节，2.01.1 更正）。
- 快照只在内存里，用于"本次操作失败回滚"，**不落盘**。

## rc=87 的定论（2026-11-27，v2.01.1）

脚本：[`scripts/topology_repro87.py`](../scripts/topology_repro87.py)。
**只读**——把 `SDC_APPLY` / `SDC_SAVE_TO_DATABASE` 换成 `SDC_VALIDATE`，
Windows 只校验"这份配置能不能设"，一个像素都不会变。所以可以安全地
在内存里模拟"断开 → 接回"，反复试。

`SDC_VALIDATE` 是本项目最有用的一件工具：**所有关于 SetDisplayConfig 的猜想，
都应该先用它验一遍再动代码。**

### 三条实测

| # | 提交形态 | rc |
|---|---|---|
| C1 | 全量 233 条（`QDC_ALL_PATHS` 原样，含 224 条未连接组合） | **0** |
| C2 | `sourceInfo.modeInfoIdx = INVALID` | **87** |
| C3 | `targetInfo.modeInfoIdx = INVALID`，source 有效 | **0** |

补充：C2 加 `SDC_PATH_PERSIST_IF_REQUIRED`(0x800) /
`SDC_FORCE_MODE_ENUMERATION`(0x1000) / `SDC_ALLOW_PATH_ORDER_CHANGES`(0x2000)
任何一个或全加，都还是 87。`SDC_TOPOLOGY_SUPPLIED`(0x10) 部分提交也是 87。

### 由此确定的两条口径

1. **source 侧 mode 是硬要求。** 想"两个都交给 Windows 挑"（`SDC_ALLOW_CHANGES`）
   是行不通的，只有 target/desktop 侧能交出去。source mode 算不出来时，
   正确做法是**不提交**并说清原因，而不是硬提交去换一个裸 rc=87。
2. **全量提交本身没问题。** "224 条未连接组合害得 full solution 校验失败"
   这个猜测是错的，不要为此引入 `SDC_TOPOLOGY_SUPPLIED`。

## 边界

- 探针不修改任何显示设置；真正断开/接回的实验必须由人执行。
- `QDC_ALL_PATHS` 官方注明"计算昂贵"，本脚本只在调研时使用，不进主程序运行路径。
- 远程/非控制台会话下 `QueryDisplayConfig` 可能返回 `ERROR_ACCESS_DENIED`，脚本会明确打印原因。
- `topology_live_check.py` 会真的把副屏断掉 1~2 秒，默认只打印计划；加 `--yes` 才执行。
