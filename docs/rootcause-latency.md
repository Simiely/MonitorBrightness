# 熄灭 / 点亮延迟根因调研（基线 v1.9.4）

> 调研对象：`monitor_brightness.py`（v1.9.4，约 4900 行，单文件）
> 症状：**「息屏响应很慢，亮屏也是。」** 两个方向都慢。
> 结论先行：**亮屏慢 = 固定 sleep 阶梯（3.85s，占 95.4%）**；**熄灭慢在当前 ddc 配置下程序侧只有 0.5–1.6ms**，慢的部分要么在固件、要么在「能力串未命中（+3.09s/台）」「进程冷启动（+2.1s）」「`_busy` 静默丢点击」这三条外围路径上。
> 本报告只做结论与方案，**未实施重构**。

## 2. 四条嫌疑：证实 / 排除

### 嫌疑 1：亮屏固定 sleep 阶梯本身就是 3 秒以上 —— **证实**

证据：

1. `_wake_one` 的 sleep 全部是**无条件**语句，没有任何"已经亮了就提前退出"的判定（L1212-1243）。唯一的提前返回是「两次基础写都失败」（L1221-1223）。
2. `expect_off=True` 的执行路径逐级打印（干跑，`_wake_trace.py`）：

```
[mon0] wvcp 0xD6=1        t=0.0ms     (桩)
[mon0] sleep 350          t=0.4→350.4
[mon1] wvcp 0xD6=1        t=350.6      ← 两线程被 DDC 串行化
[mon0] read 0x10          t=404.3  (53.9ms)
[mon0] wvcp 0x10=cur      t=458.4
[mon0] sleep 350          t=458.5→808.5
[mon0] broadcast SC_OFF   t=808.7  (桩 0.0ms)
[mon0] sleep 800          t=808.8→1608.8
[mon0] broadcast SC_ON    t=1609.0
[mon0] nudge_input         t=1609.1
[mon0] sleep 350          t=1609.2→1959.2
[mon0] read 0x60          t=2019.3  (60.1ms)
[mon0] wvcp 0x60=cand     t=2019.5
[mon0] sleep 2000         t=2019.6→4019.6
[mon0] wvcp 0x60=orig     t=4019.8
[mon0] return stage=4     t=4019.8
[mon1] …同序列，wall 4035.8ms
```

3. 每级都执行、5 个 sleep 全部走完：0.35 + 0.35 + 0.8 + 0.35 + 2 = **3.85s**；整条点亮 **4035.8ms**，固定等待 **95.4%**。
4. `expect_off=False` 时虽然跳过重驱动和切源，仍走 3 个 0.35s（1050ms，占 89.7%），并没有"已经亮了就早退"。
5. 结论：**"亮屏慢"不是 bug，是这套阶梯设计的结果**；所谓"提前退出"在本版根本不存在，所以不存在"break 条件永远为假"的问题——是根本没写 break。

### 嫌疑 2：熄灭走 `system` 时 `SendMessageTimeoutW` 的 2000ms 超时 —— **部分证实，且与当前配置无关**

证据：

1. 超时参数确实是 **2000ms**：`SendMessageTimeoutW(..., 0, 2000, None)`（L1129-1130）。
2. 当前配置走的是 **ddc**，不是 system：`config.json` 实测 `screen_off_method=ddc`；`SETTINGS` 默认值也是 ddc（L181-182）。
3. 落到 system 的条件只有一个：用户在界面/配置里显式把「熄灭方式」切成「系统级」（`screen_off_cfg` L1345-1355，二选一，**没有运行时自动回退**）。能力串未声明 `0xD6=2` 时**不会**回退 system，而是跳过该屏并报错（L1274-1279，除非 `ddc_allow_undeclared=true`，当前正是 true）。
4. 但 **点亮路径的第 3 级无条件广播两次 `SC_MONITORPOWER`**（`_output_recycle` L1246-1254），每次同样有 2000ms 超时。也就是说：即使熄灭走 ddc，**点亮仍会碰到这两条 2000ms 上限的广播**（干跑记录到 4 次广播 = 2 台 × 2）。这是"亮屏慢"里**除 3.85s 之外的第二个可变上界**（最坏 +4s，通常 0ms，取决于是否有窗口卡住）。
5. 结论：**"熄灭走 system 导致 2 秒等待"——当前配置下不成立（排除）；"广播超时 2000ms 是真实存在的可变开销"——成立，但作用在点亮第 3 级，不在熄灭**。

### 嫌疑 3：点击到第一条命令之间的 GUI 线程占用（同步枚举） —— **排除（但发现另一个真问题）**

证据：

1. 点击回调链：`screen_off()` → `selected_indices()`（纯控件状态，L3979-3980）→ `run_bg()` 起线程（L4025-4039）。**回调里没有 `refresh_monitors`、没有 `enumerate_targets`、没有 DDC 调用**。
2. 枚举发生在**后台线程内**（`screen_off_cfg` → `screen_off_many` → `enumerate_targets`），实测 0.37–1.4ms，不占 GUI 线程。
3. 干跑打点：回调进入 → 线程首次执行 <1ms；点击到首条命令 `≈0.5–1.6ms`。
4. 但有一个**不是枚举**的 GUI 侧问题：`run_bg(busy=True)` 会立刻 `_busy=True` 并禁用三块面板（L4026-4028），而 busy 窗口覆盖**整个后台任务时长**（点亮约 **4s**）。这 4s 内用户再点「熄灭/点亮」，`screen_off`/`screen_on` 顶部直接 `return`（L4263-4264、L4290-4291）——**静默丢弃，没有任何提示**。用户的主观描述很容易就是"点了没反应，过几秒才黑"。
5. 结论：**GUI 同步枚举的嫌疑排除**；**`_busy` 静默丢点击是独立且真实的问题**（属于交互补丁，不属于 DDC 延迟）。

### 嫌疑 4：`DEV#EDID` 缓存 key 是否每次现读 EDID —— **排除（当前不付费），并纠正命名**

证据：

1. 本机实际 key 不是 EDID 本体，而是 `DISPLAY1#<DeviceID 的 sha1 前 8 位>`；代码注释明确写了本机 `Device Parameters\EDID` 不存在，改用 `EnumDisplayDevicesW` 的 `DeviceID`（L744-775）。
2. `_display_uid` 第一次算完就写入进程内 `_EDID_CACHE`，之后同一 `dev` 直接命中（L758-759、L774）——**同一进程生命周期内只读一次**，满足要求。
3. 实测：冷 1.19–1.31ms/台，热 0.39ms/两台；对 4s 的唤醒阶梯而言可忽略。
4. 真正会周期性付费的是**能力串**：`_capabilities_cached` 命中 0ms；未命中时实测 **3087ms / 3098ms 每台**（L717-729、L792-801）。当前 `config.json` 的 4 个 caps 键都带 `#` 且命中，所以熄灭首条命令前不付这 3 秒；但**只要 caps 键失配**（换线、换面板、旧版 dev-only 键、配置被覆盖），首次熄灭就会 **+3.09s/台、串行**，2 台约 **6.2s**，这才是历史上"熄灭要 6 秒"的根因，也是现在最容易复发的慢路径。
5. 结论：**EDID 现读——排除；能力串 miss——确认为最大的单点可变开销**。

## 3. 程序侧 vs 显示器固件：用户说"慢"，该算谁的

| 场景 | 程序侧可测耗时 | 固定等待占比 | 固件/系统侧 | 归因 |
|---|---|---|---|---|
| 熄灭 ddc（当前配置、caps 命中） | **0.5–1.6ms** | 0 | 真实 `SetVCPFeature` 往返（未测）+ 面板背光关闭延迟（未知） | **程序侧 <0.1%**。若用户感知"几秒"，几乎全部在固件或外围路径 |
| 熄灭 ddc（caps 未命中） | **+3.09s/台（串行）** | 100%（读能力串） | 同上 | **程序侧占绝对多数**（6.2s/2 台） |
| 熄灭 system | 0–2000ms（广播超时） | 可变 | 系统投递 + 固件 | 程序侧最多 2s，且只在选了 system 时 |
| 点亮（`expect_off=True`） | **4035.8ms** | **95.4%** | 面板唤醒（未知） | **程序侧 100% 可解释"慢"**（4.0s 是我们自己等的） |
| 点亮（`expect_off=False`） | **1170.2ms** | **89.7%** | 同上 | 程序侧为主 |
| 到点熄屏（任务路径） | **+2.05–2.23s 冷启动** | — | 之后同第一行 | 程序侧为主（启动成本） |

一句话：**亮屏慢 100% 能归因到程序侧固定等待；熄灭慢在当前配置下程序侧几乎没有责任，责任在"能力串 miss / 冷启动 / `_busy` 丢点击"这三条外围路径，以及我们测不到的固件。**

## 4. 补丁清单与逐条判断

判定口径：
- **根因修复** = 解决了真实机制问题，应保留；
- **临时补丁** = 为绕开某次事故加的保险/兜底，保留但属于债；
- **必须重构** = 同一逻辑多套实现或不可测试，继续加补丁只会更糟。

| # | 补丁点 | 证据 | 判断 |

## 5. 该修根因还是该重构

### 5.1 结论

**先修根因里的"设计缺陷"，再对屏幕动作做局部重构；不做全量重写。**

理由：

1. 亮屏慢的根因是**阶梯没有判据、没有早退**（P3 + P6），这是设计层面的问题，补丁修补丁（再加一个 sleep、再换一套方法）只会更慢。
2. 熄灭慢的根因**不在熄灭代码**，而在 caps 未命中（P8 的 miss 路径）、进程冷启动、`_busy` 丢点击（P11）。这三条都能在不碰屏幕时序的前提下单独修。
3. P1/P2/P5/P6 已经构成"同一件事四套写法"，且**没有可回放的调用序列测试**——这正是"补丁修补丁"的土壤。局部重构（把策略/计划/执行拆开）能一次性让"延迟"和"失败回退"变成可测对象。

### 5.2 最小可行重构边界（先拆哪一块，为什么）

**第一刀只拆屏幕动作，命名 `screen_ops`（单文件内分节即可，不必拆包）：**

```
┌ 策略层 plan_policy(cfg, state) -> Plan
│   输入：screen_off_method / wake_switch_input / screen_state / caps
│   输出：有序 Step 列表（方法、参数、判据、最大等待）
├ 执行层 execute(plan, io) -> Result
│   io 是注入接口：read_vcp / write_vcp / broadcast / sleep / nudge
│   每步记录 (op, args, wait_ms, t0, t1)
└ 结果层 Result(ok, stage, message, trace)
     GUI / CLI / 计划任务 三条入口只消费 Result
```

为什么**先拆它**：

- 所有可测延迟都在这条链上（4.03s / 1.17s / 2ms），拆完立刻能出"每步毫秒"；
- 它是唯一碰硬件的边界，注入 `io` 后可以**完全打桩**跑测试（当前测试不敢碰它，只能 AST diff）；
- GUI（`screen_off`/`screen_on`）、CLI（`--apply-schedule`）、任务（exe 启动）共用同一入口，改一次三处受益；
- 不动 UI、不动配置、不动任务注册，爆炸半径最小。

**第二刀（可后置）**：任务注册 P13 单独拆 `task_reg`，用真实的 `Register-ScheduledTask` cmdlet 参数对象替代字符串拼接。它与延迟无关，但它是另一堆补丁。

### 5.3 硬约束（重构不得改变用户可见行为）

1. 默认仍是 `screen_off_method=ddc`；`screen_off_many` 的"先查能力串、未声明就跳过"逻辑一字不改。
2. 熄灭 ddc 仍只发 **一条** `SetVCPFeature(0xD6=2)`/台，顺序、参数、串行循环不变。
3. 点亮级数与顺序不变：`0xD6=1` → 读/写 `0x10` → 重驱动输出（`expect_off` 时）→ 输入注入 →（允许且记账熄过时）切 `0x60` 往返。
4. **所有 sleep 时长不变**（0.35/0.35/0.8/0.35/2）。"提前退出"属于**行为变更**，必须单独评审、单独版本，不许夹带进重构。
5. 失败语义不变：两次基础写都失败 → `(False, 0, "显示器未响应 DDC/CI（电源 / 亮度写入均失败）")`；切源失败 → "切信号源失败（前几级已下发）"；错误文案与 `stage` 编号不变。
6. 无跨方法自动回退（P4 已证实不存在），重构后也不许新增。
7. GUI 侧 `_busy`、150ms 轮询、`save_config` 调用点不变（除非另开一项）。

### 5.4 等价性验证方法

**Golden 调用序列比对（可离线、零硬件动作）：**

1. 先给当前 v1.9.4 录基线：注入 `FakeIO`，对下面 10 个用例各跑一次，记录 `[(op, args, wait_ms)]` 与 `(ok, stage, msg)`：

   | 用例 | 配置/条件 |

   | C2 | off + ddc + caps 未命中 |
   | C3 | off + ddc + 能力串未声明 `2` + `allow_undeclared=false` |
   | C4 | off + ddc + 首台写失败 |
   | C5 | off + system（广播成功） |
   | C6 | off + system（广播失败） |

2. 重构后跑同一组，**逐条比对**：序列长度、每步 `op/args`、`wait_ms`、返回三元组。要求 **10/10 完全一致**。
3. 任何差异必须写进白名单并说明"为什么这是允许的"，否则视为回归。
4. 附加：19 项单测 + `--selftest`（只读）+ AST diff（现有 30 项屏幕/GUI 函数与 v1.8.5 的对照脚本 `_diff_screen_path.py` 继续保留）。
5. 全流程**不执行任何真实写/广播**；需要真机确认时，仍用干跑打点（用户自己点一次，屏幕不动）。

## 6. 结论摘要（给决策用）

- **亮屏慢**：`_wake_one` 在 `expect_off=True` 时**无条件**走 5 个 sleep，共 **3.85s（95.4%）**，无任何提前退出；`expect_off=False` 也要 **1.05s（89.7%）**。这是设计结果，不是偶发 bug。另有两条 `SendMessageTimeoutW` 的 2000ms 上限（第 3 级重驱动）可能再加最多 4s（多屏、卡窗口时）。
- **熄灭慢**：当前 ddc + caps 命中下程序侧仅 **0.5–1.6ms**。真正会慢的路径是：caps 未命中 **+3.09s/台（串行，2 台 ≈6.2s）**；任务触发时 exe 冷启动 **+2.1s**；点亮后 `_busy` 4s 窗口内点击被**静默丢弃**；仅当用户选 system 时才有广播 **2000ms** 超时。
- **该修根因还是重构**：两条都做，但顺序是"**先修 P3/P6 的设计缺陷（判据 + 早退，单独版本）**，再做**局部**重构（`screen_ops` 策略/计划/执行分离；`task_reg` 后置）"；不建议全量重写 4900 行单文件。
- **补丁密度**：属实，但集中在屏幕动作（P1/P2/P3/P5/P6）与任务注册（P13）；其余部分不需要动。
- **本次是否动过屏幕**：**没有**。未写 `0xD6`/`0x10`/`0x60`、未广播 `SC_MONITORPOWER`、未 `ES_DISPLAY_REQUIRED`、未注入真实鼠标键盘；所有写调用均为打桩打点。

### A.6 「阶梯早退」到底划不划算

| 项 | 数字 |
|---|---|
| 判据成本 | **≈58ms/次**（`0xD6` 或 `0x10`） |
| 理论收益 | 若 4 个检查点各读 1 次 = **232ms**，最多省下 3.85s → **≈3.6s** |
| **实际可行性** | **不成立**：本机 `0xD6` 5/5 次全返回 `1`，而历史事故中**背光已灭时回读仍是 `1`**；`0x10`（亮度）在待机状态下**同样可读**。两个只读量都**不能证明"面板已亮"** |
| 结论 | **成本不是障碍，可信度才是**。用 DDC 读值做早退，等于把 v1.7.0 的"程序说亮了、屏幕其实黑着"重新写回来 |

可行的替代（都不依赖"撒谎的判据"，但**都改变用户可见时序，需单独批准**）：

1. **分级升级**：首次唤醒只走短路径（`0xD6=1` + 写亮度 + 输入注入，约 **0.7s**）；用户再点一次仍未亮，才升级到重驱动 + 切源（再付 ~3s）。用"用户再点"替代"DDC 判据"，把 4.0s 的常态降到 0.7s。
2. **缩短无条件等待**：0.8s 重驱动间隔、0.35s 步间等待按本机实测下调（需逐项验证固件仍能醒）。
3. **系统级信号只对 system 模式有效**：`GUID_CONSOLE_DISPLAY_STATE` 这类系统电源状态在 DDC 待机后仍报"开"（Windows 不知道面板被 DDC 关了），**不能用于 ddc 模式**。
4. **缩短/去掉 `0x60` 往返**：2s 是点亮路径里最大的一块，但它是唯一能救"切到空口"的手段，删除属于行为变更，需用户明确同意。

补充风险（与延迟无关但必须记录）：两台面板的 `0xD6` 只声明 `01 04 05`，**当前 ddc 熄灭写的 `2` 是未声明值**，仅因 `ddc_allow_undeclared=true` 才被放行。这是稳定性风险，不是"慢"的根因。
