# 重构计划（基于结构审计，2026-11-27）

> 目标：把"想起一处做一处"的缠绕理成清晰模块，**不改变任何用户可见行为**。
> 铁律：每一步都可独立提交、独立回退；178 个单测是底线。
>
> **v2（复核后修正）**：初审版有两个致命缺陷（见文末「复核记录」），
> 已改 P0 目的、去掉 P1 的防抖、补 P2 接口设计与提交粒度。

## 零、优先级（按用户定的「稳定第一、轻量第二」重排）

| 序 | 动作 | 对稳定的作用 | 对轻量 | 风险 |
|---|---|---|---|---|
| 1 | **P0 补 19 条关键测试** | **高**：将来任何改动都有护栏 | 0 | 无 |
| 2 | **P1 配置写入单点** | **高**：消除 18 处各写各的状态不一致 | 0 | 低 |
| 3 | **P0b 静默异常审计（41 处 `except: pass`）** | **高**：失败能被看见、能诊断 | 0 | 低 |
| 4 | P2 抽服务（App 89→25） | 中：长期减少"改一处崩三处" | 0 | **高** |
| 5 | P4 拆巨型函数 | 低：纯可读性 | 0 | 低 |
| 6 | P3 拆文件 | **低：不影响运行时稳定** | 0 | 中 |
| 7 | Tcl/Tk 裁剪 | 0 | +1~2 MB（估计） | 中（可能缺编码/字体） |

**说明**：P3（拆文件）提升的是"可读性和并行开发"，不是"跑起来更稳"。
按"稳定第一"的原则，它应排在**有测试护栏之后**，且优先级最低。
轻量方面，15.2 MB 已经是 onefile + 39 个 `--exclude-module` 的结果，
继续压的收益（1~2 MB）小于风险（裁掉编码/字体导致异常），**建议不动**。

## 一、审计结论（实测数据，不是感觉）

| 指标 | 数值 | 判断 |
|---|---|---|
| 总行数 / 函数 / 类 | 8290 / 443 / 42 | 单文件过大 |
| **`App` 类** | **89 方法 / 1381 行** | **God Object，核心问题** |
| `topology_off` | 176 行 / 扇出 36 | 最复杂的单函数 |
| `App.__init__` | 114 行 | 装配与业务混写 |
| `save_config` 调用点 | **18 处** | 配置写入分散 |
| `dlog` / `_write_event_log` | 51 / 11 处 | 分散但**正常**（日志本就该随处可写） |
| 职责混杂函数（同函数既 UI 又硬件） | **8 个（2%）** | 字符串粗估，见文末局限 |
| 模块级可变全局 | 17 个，写入点均 ≤2 | **不是主要问题** |
| **函数级双向调用（A↔B）** | **0 对** | **没有循环依赖泥潭** |
| **`App` 方法被测试直接覆盖** | **24 / 89（27%）** | **最大风险：73% 裸奔** |

**结论（修正后）**：真实问题不是"循环依赖"，而是两件事 ——
① **`App` 是 God Object**（89 方法吞掉装配/业务/事件/托盘/定时）；
② **待拆代码大部分没有测试护栏**（App 的 73%、`topology_on` 与
`build_register_script` 完全零覆盖）。

所以重构的性质是「**按职责拆分 + 补测试护栏**」，不是"解开环"。

## 二、目标与非目标

**做**
- 依赖方向单一：`ui → domain → win32`，底层不认识上层
- `App` 从 89 方法降到 **≤25**（只留装配、事件分发、状态提示）
- 配置写入收敛到 1 个入口（**但写盘时机不变**）
- 巨型函数拆到 ≤60 行
- **关键路径测试覆盖率补到 90% 以上**（这是前置条件，不是副产品）

**不做**
- 不改任何用户可见行为（交互、文案、默认值、配置文件格式、**写盘时机**）
- 不换 UI 框架（已实测：8.1× 体积 / 2.5× 启动 / 2.6× 内存）
- 不顺手"优化"业务逻辑

### P0b · 静默异常审计（稳定性收益最直接的一项）

全文件 **118 处 `except`，其中 41 处是 `pass`**（静默吞掉）。不是所有 `pass`
都错——"释放句柄失败""DWM 不支持深色标题栏"这类忽略是合理的。但要逐个分类：

| 类别 | 处理 |
|---|---|
| 资源清理（CloseHandle/DestroyPhysicalMonitor） | 保留 `pass`（失败也确实无能为力） |
| 能力探测（DWM、shcore 不可用） | 保留，但可以 `dlog` 一次 |
| **业务写操作（SetVCPFeature / SetDisplayConfig / save_config）** | **必须记日志或上报**：现在失败了用户只看到"点了没反应" |
| 配置读取/解析 | 已有备份+提示，核对无遗漏 |

**做法**：写一个脚本列出 41 处的（文件行号、所在函数、异常类型、上下文一行），
人工分类后，只改"业务写操作"那一类。**不改异常处理结构，只补日志/上报**。

**验证**：新增测试——模拟 `SetVCPFeature` 抛异常，断言事件日志里有记录
（现在这类失败可能静默）。

**验证**：新增测试自身也要验证"能抓错"（故意改坏一处，确认测试变红）。

### P1 · 收敛配置写入（**去掉防抖**）

新增 `domain/config.py`：

```python
class ConfigStore:
    def load(self) -> dict
    def save(self, cfg: dict) -> tuple[bool, str]   # 保持原子写，不加防抖
    def snapshot(self) -> dict                      # 只读副本
```

- **保留模块级 `save_config(cfg)` 签名**，内部转调 `ConfigStore.save`：
  18 个调用点**一行都不用改**，风险最低。
- **不加防抖**：初审想加，但防抖会改变"改完立刻退出"的写盘时机，
  属于用户可见行为变化（可能丢配置），违反铁律。真要防抖，必须配
  "退出时 flush"，那是另一个需求。
- 收益：写入逻辑单点（原子写/备份/错误上报只在一处），
  而不是"18 处各写各的"。

**验证**：`test_config.py` 全绿；新增"18 处调用点行为等价"的对比用例。

### P2 · 抽服务层（`App` 89 → ≤25，最关键一步）

**先定接口，再搬实现**（初审缺这一步，最容易变成"搬方法不搬依赖"）。

服务不使用 tkinter，通过**回调**通知 UI：

```python
# domain/screen.py
class ScreenService:
    def __init__(self, cfg_getter, on_busy_changed, on_done, on_error):
        ...
    def off(self, indices) -> None      # 内部起线程，结果回调
    def on(self, indices) -> None
    def probe(self) -> None
```

- 服务**只持回调**，不持 widget；App 把回调接到 `status_var` / 面板刷新
- 每个服务**单独一个 commit**（3 个服务 = 3 次提交），
  任一失败只回退一个，不是整批

| 服务 | 吸收的方法 | 依赖 |
|---|---|---|
| `ScreenService` | 屏幕/亮度 12 + 探测/状态 9 = **21** | win32: ddc、ccd、display |
| `ScheduleService` | 定时/任务 11 + 部分设置 4 = **15** | domain: config、tasks |
| `LayoutService` | 拓扑/恢复 12 | win32: ccd、domain: config |

`App` 保留：装配、`run_bg`/队列、`_fit_window`、`_on_close`、
`_report_tk_error`、`open_*`、`_build_*` —— 约 **22 个**。

**验证**：每个服务单独测试（不需要 Tk 环境）。

## 四、风险与止损

| 风险 | 概率 | 止损 |
|---|---|---|
| **待改代码无测试，改完不知不觉变行为** | **高** | **P0 先补 19 条关键测试，不补完不进 P2** |

| 重构期用户想用旧版 | 低 | `dist/` 始终可运行；每阶段 commit 可回退 |

## 五、审计方法的局限（诚实标注）

| 局限 | 影响 | 处理 |
|---|---|---|
| "职责混杂 2%" 是**字符串匹配**（`"tk." in body`） | 注释/字符串会误命中；`from tkinter import` 后的直接调用会漏 | 只当参考，不作为拆分依据 |
| 扇出统计含内置函数（`len`/`print`） | "36 个调用"可能高估 | 拆函数时以实际代码为准 |
| 双向调用检测把 `Canvas.delete`、`BooleanVar.set` 误当函数 | 报了 6 个假环 | 已人工核对，**真实双向调用为 0** |
| 未做行级覆盖率（无 coverage 工具） | "65 个未测"是"未被直接调用"，不等于"完全没执行到" | P0 补测试时以"关键路径"为准 |
