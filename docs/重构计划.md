# 重构计划（基于结构审计，2026-11-27）

> 目标：把"想起一处做一处"的缠绕理成清晰模块，**不改变任何用户可见行为**。
> 铁律：每一步都可独立提交、独立回退；178 个单测是底线。

## 一、审计结论（实测数据，不是感觉）

| 指标 | 数值 | 判断 |
|---|---|---|
| 总行数 / 函数 / 类 | 8290 / 443 / 42 | 单文件过大 |
| **`App` 类** | **89 方法 / 1381 行** | **上帝对象，核心问题** |
| `topology_off` | 176 行 / 扇出 36 | 最复杂的单函数 |
| `App.__init__` | 114 行 | 装配与业务混写 |
| `save_config` 调用点 | **18 处** | 配置写入分散 |
| `dlog` / `_write_event_log` | 51 / 11 处 | 分散但**正常**（日志本就该随处可写） |
| 职责混杂函数（同函数既 UI 又硬件） | **8 个（2%）** | 比预想好 |
| 模块级可变全局 | 17 个，写入点均 ≤2 | **不是主要问题** |

**结论修正**：缠绕不在"全局状态污染"，而集中在三处 ——
① `App` 一个类吃掉 89 个方法；② 4 个 >100 行的巨型函数；③ 配置写入 18 处。

所以重构的重点是**拆 `App`**，而不是"消灭全局变量"。

## 二、目标与非目标

**做**
- 依赖方向单一：`ui → domain → win32`，底层不认识上层
- `App` 从 89 方法降到 **≤25**（只留装配、事件分发、状态提示）
- 配置写入收敛到 1 个入口
- 巨型函数拆到 ≤60 行
- 模块可独立测试

**不做**
- 不改任何用户可见行为（交互、文案、默认值、配置文件格式）
- 不换 UI 框架（已实测论证：8.1× 体积 / 2.5× 启动 / 2.6× 内存）
- 不顺手"优化"业务逻辑（那是另一个决策）

## 三、分阶段计划

### P0 · 安全网（先建护栏，再动刀）

1. **架构守护测试**：断言依赖方向
   - `core/win32/**` 不得 import `ui` / `tkinter`
   - `domain/**` 不得 import `tkinter`
   - `ui/**` 不得直接 import `core.win32`（只能经 domain）
2. **行为基线快照**：把 `--list`、`--selftest`、`--diag` 的当前输出存成文件，
   重构后逐字比对（这些是纯只读命令，安全）
3. 把 178 个测试按模块打标签（`@tag("config")` 之类），便于分模块回归

**验证**：新增守护测试自身要能"抓到你故意违规"（写一个反例验证它会红）。

### P1 · 收敛配置写入（18 处 → 1 处）

新增 `domain/config.py`：

```python
class ConfigStore:
    def load(self) -> dict
    def update(self, **kw) -> None      # 改内存 + 落盘（原子写 + 防抖）
    def snapshot(self) -> dict          # 只读副本
```

- 18 处 `save_config(cfg)` 逐步换成 `store.update(...)`
- **防抖**：连续多次改（如拖动滑块）合并成一次写盘，减少 IO
- 保留 `load_config()` 作为兼容入口，内部转调 `ConfigStore`

**验证**：`test_config.py` 全绿 + 新增"连续 update 只写一次盘"用例。

### P2 · 抽服务层（`App` 89 → ≤25，最关键一步）

按审计的职责分组，抽出三个服务（纯 Python，不碰 tkinter）：

| 服务 | 吸收的方法 | 依赖 |
|---|---|---|
| `ScreenService` | 屏幕/亮度 12 + 探测/状态 9 = **21** | win32: ddc、ccd、display |
| `ScheduleService` | 定时/任务 11 + 部分设置 4 = **15** | domain: config、win32: tasks |
| `LayoutService` | 拓扑/恢复 12 | win32: ccd、domain: config |

`App` 保留：`__init__` 装配、`run_bg`/队列、`_fit_window`、`_on_close`、
`_report_tk_error`、`open_*`、`_build_*` —— 约 **22 个**。

**关键约束**：服务通过**回调/事件**通知 UI（不持有 widget），
UI 只读服务状态。这样服务和 UI 彻底解耦。

**验证**：每个服务单独写测试（不需要 Tk 环境）。

### P3 · 拆文件（机械操作，纯移动）

```
monitor_brightness.py        # 入口，<100 行
core/win32/ddc.py            # DDC/CI（亮度、电源、能力串）
core/win32/ccd.py            # 拓扑（查询/规划/应用/回读）
core/win32/display.py        # 枚举、HMONITOR、EDID
core/win32/system.py         # DWM、单实例、输入、系统熄屏
domain/config.py             # ConfigStore + 迁移 + 校验
domain/screen.py             # ScreenService
domain/schedule.py           # ScheduleService
domain/layout.py             # LayoutService
domain/tasks.py              # 计划任务注册/比对/自愈
ui/theme.py                  # UI 字典、字体、DPI
ui/widgets.py                # Button/Switch/Segmented/Tooltip/...
ui/panels.py                 # MonitorPanel/BrightnessPanel/SchedulePanel
ui/sheets.py                 # SettingsSheet/SlotEditor/HeirSheet
ui/app.py                    # App 壳
cli.py                       # 命令行
```

**做法**：一次只搬一个模块，搬完立刻跑测试 + 改 import，提交。
不追求"一次到位"，允许中间状态有兼容 shim。

### P4 · 拆巨型函数

| 函数 | 现在 | 拆成 |
|---|---|---|
| `topology_off` | 176 行 | `_snapshot` / `_plan` / `_activate_heir` / `_apply` / `_verify` |
| `ccd_probe_topology` | 103 行 | `_query` / `_parse_targets` / `_parse_sources` |
| `App.__init__` | 114 行 | `_init_state` / `_build_ui` / `_bind` / `_startup` |
| `apply_dark_theme` | 88 行 | 主题字典移到 `ui/theme.py`，函数只剩应用 |

### P5 · 验收

1. 178 测试全绿（+ 新增守护/服务测试，预计 200+）
2. `--list` / `--selftest` / `--diag` 输出与基线逐字一致
3. 打包 + `--selftest` + 真机跑一次熄/亮
4. `App` 方法数 ≤25、最大函数 ≤60 行（审计脚本复测）

## 四、风险与止损

| 风险 | 概率 | 止损 |
|---|---|---|
| P2 抽服务时 UI 与 App 循环引用 | 高 | 先定接口再搬实现；服务不 import tkinter；用 `Protocol` 描述回调 |
| 拆文件时漏改 import 导致运行时报错 | 中 | 每搬一个模块立刻 `py -m py_compile` + 全量测试 |
| 隐性行为改变（如配置写入时机） | 中 | P1 只改"写入口"，不改"何时写"；基线快照比对 |
| 重构期间用户想用旧版 | 低 | `dist/` 始终保持可运行版本；每阶段提交可回退 |

**硬止损规则**：任一阶段测试转红且 30 分钟内修不回 → `git revert` 该阶段，不硬撑。

## 五、预估

| 阶段 | 主要内容 | 风险 |
|---|---|---|
| P0 | 守护测试 + 基线 | 低 |
| P1 | 配置写入收敛 | 低 |
| P2 | 抽服务、App 瘦身 | **高** |
| P3 | 拆文件 | 中（量大但机械） |
| P4 | 拆巨型函数 | 低 |
| P5 | 验收 | 低 |

规模上这是"重排 8000 行"的活，不是重写；用户可见行为零变化。
