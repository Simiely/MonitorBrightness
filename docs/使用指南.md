# 使用指南

面向使用者的详细说明：定时机制、命令行长什么样、熄灭/点亮到底做了什么、

## 定时可靠性

### v2.02.0：档位可以只在指定星期生效

每个时间段都能单独勾「重复」：周一…周日。不勾任何一个 = **每天**（与旧版完全一致，
旧配置不需要迁移）。

- **任务计划**层面：只在指定星期时注册 `-Weekly -DaysOfWeek ...`，任务计划程序里
  能直接看到"只在周一、三、五"；选满 7 天仍按 `-Daily` 注册（与旧版一致）。
- **执行**层面再判一次：登录校准任务、或卸载残留的任务不经过 Weekly 触发器，
  到点会自己检查"今天是不是这一档的星期"，不是就直接退出。
- **下次运行**按真实星期推算：周五晚上看"仅周一"的档，会显示「周一 08:30」，
  不会说成"明天"。
- 改了星期会自动重建任务（`task_match_reason` 比对触发星期，不只是时点）。

### v1.9.0 / v1.9.4：启动自愈（只检查，不执行）

v1.8.x 之前只有手动点「应用」才会重建计划任务。发版换目录（`dist_v185` → `dist_v186`）
后，任务动作仍指向旧 exe：任务"跑了"，但找不到程序，用户看到的就是**到点没执行**。
v1.9.0 的修法：

1. **启动自愈**：每次启动读一次任务 XML（路径、参数、触发点、`StartWhenAvailable`），
   与当前进程不一致就**静默重建**——换目录、改名、重装都不用手动点开关。
2. **原地更新**：任务已存在时优先 `Set-ScheduledTask`（保留上次运行记录），
   失败才回退卸载重注册；旧实现每次都先删后建，会把"上次运行"重置成"从未运行"。
3. **启动自检只检查任务配置**（v1.9.4）：v1.9.0 曾额外做"今天错过的档位补执行"，
   已被撤销。**本程序启动时不会主动熄屏，也不会改亮度**；配置一致时状态行只显示
   「定时任务已就绪，下次运行 X」，不弹窗。
4. 界面任务状态行同时显示**下次运行 / 上次运行 / 上次结果**，下面是事件日志
   （任务重建、配置恢复都可见）。

### v1.1.0：错过补跑

v1.0.0 有个明确的缺陷：**电脑在设定时间点处于关机 / 睡眠状态时，到点那次调节会永远丢掉**。
原因是它用 `schtasks.exe` 注册任务，而 **`schtasks.exe` 命令行根本没有「错过就尽快补跑」这个开关**。

v1.1.0 的修法：

1. 改用 PowerShell `Register-ScheduledTask` + `New-ScheduledTaskSettingsSet -StartWhenAvailable`；
2. 任务动作统一改成 `--apply-schedule`，由**程序自己按执行时刻**判断该用哪一档。
   这样即便多条任务被同时补跑，结果也一致，不会互相覆盖；
3. 额外注册一条「登录后自动校准」任务：登录后 30 秒执行一次 `--apply-schedule`，
   保证**开机时间已经晚于切换点**时也能立刻补上。

> 官方文档事实：错过的任务会被排入队列，**默认延迟 10 分钟**才启动
> （`TaskSettings.StartWhenAvailable` 备注），所以补跑不是"立刻"。

## 命令行模式（供任务计划调用）

```bat
:: 立即设置（序号可写 all 或逗号分隔的多个）
MonitorBrightness.exe --set 0 50
MonitorBrightness.exe --set 0,1 50
MonitorBrightness.exe --set all 50

:: 按当前时间判定档位后下发（计划任务用的就是这条）
MonitorBrightness.exe --apply-schedule

:: 列出显示器（带当前输入源）/ 实测亮灭 / 只读诊断
MonitorBrightness.exe --list
MonitorBrightness.exe --probe
MonitorBrightness.exe --diag

:: 打印最近的诊断日志（排障用；设置里可以整体关掉）
MonitorBrightness.exe --diag-log

:: 打印档位判定自检表
MonitorBrightness.exe --selftest

:: 按当前配置/当前 exe 重建计划任务（发版换目录后无界面自愈，也可排障）
MonitorBrightness.exe --ensure-schedule

:: 熄灭 / 点亮 / 只看状态
MonitorBrightness.exe --screen off
MonitorBrightness.exe --screen on
MonitorBrightness.exe --screen status
```

退出码：`0` 成功 · `1` 下发失败 · `2` **参数不合法**（亮度必须是 0-100 整数，序号必须是
`all` 或 `0,1` 这类写法——写错会直接报错退出，不会"猜"成 0 或"全部"）。

## 常见问题（完整版）

**多显示器认不出是哪台？**
列表里每行都带**型号 · 分辨率 · 主/副屏 · 设备名**（如
`Legion R27qe Gen2 · 2560×1440 · 主显示器 · DISPLAY1`），同型号双屏也能区分。

**「当前亮度」一直是 `--`？**
型号名（MCCS 能力串）实测约 3 秒/台，界面会在后台异步补；若长时间为空说明该显示器
不返回 DDC/CI 数据（点「检测」重试；型号读取有缓存，第二次起秒出）。

**动鼠标会把屏幕弄亮吗？会。** 系统级熄灭等价于 Windows 自己的"关闭显示器"
（微软文档写明 `SC_MONITORPOWER` 的 `-1 / 1 / 2` 分别是 点亮 / 低功耗 / 关闭），
所以任何键鼠输入都会把它唤醒。

| 熄灭方式 | 别人动键鼠 | 本地面板 | 远程画面 | 变砖风险 |
|---|---|---|---|---|
| **拓扑断开（默认）** | 不亮（设备从桌面移除） | 灭 | **正常**（远控抓的是接任的那块屏，通常是虚拟屏） | 无（不写面板电源命令） |
| 单屏待机 | 不亮 | 灭 | 通常正常；深度睡眠面板可能掉（见下） | 取决于面板 |
| 系统级 | **会亮** | 灭 | 可能丢帧 | 无 |

**远程画面到底会不会黑？** 决定因素不是"物理屏还是虚拟屏"，而是
**远控抓的那块屏还在不在线**（依据见下）：

- 远控抓「主显示器」或使用自带虚拟屏 → 拓扑断开后主屏已交给在线虚拟屏，
  抓到的是虚拟屏画面，**正常**。ToDesk 官方帮助中心就写明：虚拟屏开启后
  "原显示器会显示黑屏"，远程不受影响，且"可以直接把物理显示器关掉，
  只靠虚拟屏运行"。
- 只有把输出名**写死**成被断开的那块物理屏时才会失败 —— 例如 Sunshine 的
  `output_name = \\.\DISPLAY1`。Sunshine 默认是"选默认显示器"，不写死就没问题。
- **Windows 11 24H2 起有个已知回归**：如果"当前选中的显示器"离线或断电，
  DXGI 会整体初始化失败（Sunshine issue #5673、社区补丁 24H2DummyFix 都记录了）。
  所以关键永远是"有没有一块在线的屏接任"，而不是用哪种熄灭方式。

**那 DDC 单屏待机呢？** 面板待机时信号线仍连着、EDID 仍可读，Windows 一般
仍认为它在，远程不受影响 —— 这也是本程序早期默认它的原因。但部分"深度睡眠"
显示器（某些电视）待机后会断开同步，在 24H2 上反而可能触发上面那条 DXGI 回归。
所以现在的默认是**拓扑断开**：它一定会留一块在线屏（虚拟屏或另一块物理屏），
确定性最高。

**串流想只留虚拟显示器？** 用「拓扑断开」（默认就是它）。
它把选中的屏从 Windows 桌面拓扑里移除，并写入系统数据库；点亮时**现读当前拓扑**、
按锚点把这块屏加回去，回读 ACTIVE 之后再写亮度。虚拟屏 VDD 永不作**断开目标**。
命令行 `--screen off|on` 与定时档位都可用这个方式。

**主屏也能断开吗？** 能。Windows 不允许把主显示器从桌面移除（实测 `rc=87`），
但主屏说到底就是"桌面原点 `(0,0)` 所在的那块屏"，所以可以先让另一块屏挪到
`(0,0)` 接任主屏，再把原来那块摘掉 —— 全程纯拓扑操作，**不碰面板电源**，
也就没有 DDC 待机唤不回的风险。点主屏那行的「熄灭」时会弹窗问「把主屏交给谁」：

- 选一块物理屏：它挪到桌面原点成为新主屏，其余屏跟着平移，相对布局不变。
- 全部物理屏都要断开时：主屏交给虚拟显示器（串流就只剩它）。

**每行右边的「熄灭」「显示」是干什么的？** 只动这一台，不用先勾选、也不改你的勾选。
- 「熄灭」：按当前熄灭方式只关这一块。拓扑模式下副屏会被从桌面移除（主屏那行没有这个按钮，
  Windows 不允许移除主屏）；系统级模式下所有逐台按钮都不显示，因为它是整组广播。
- 「显示」：把这一块点亮。拓扑模式下就是"把断开的那块接回桌面"。

**接回后副屏会跑回原来的位置吗？** 会。断开之前程序会把这块屏当时的桌面位置记一笔
（`monitor_positions`），接回时摆回去；只有当你在这期间改过布局、导致原位置会和别的屏重叠时，
才退回桌面最右边。这笔记录每断开一次就按当下的真实值重写一遍，所以你在 Windows 里挪过屏，
它不会拿旧位置硬套。

> **v2.01.0 起接回不再"恢复断开前的快照"。** 你在断开期间于 Windows 设置里改过的
> 分辨率、排布、主屏，接回后都会保留——因为接回只是"把这块屏加回当前拓扑"，
> 不是"把整份拓扑倒回上一次"。程序不保存、也不维护任何屏幕亮灭状态。
> （位置是例外：断开后 Windows 就把这块屏的位置信息删了，不事先记一笔就无从得知；
> 它记的是"摆在哪"，不是"亮没亮"。）

**配置放在哪？** v2.01.17 起 `config.json` 和默认布局快照也在**程序所在目录**
（便携版：整个目录拷走设置就跟着走）。程序目录不可写时才回退到 `%APPDATA%`。

> **从旧版本升级**：旧版配置在 `%APPDATA%\MonitorBrightness\config.json`，
> 程序**不会自动搬**（每台电脑的配置各自独立，自动搬容易互相覆盖）。
> 想沿用旧设置：退出程序，把那个 `config.json` 复制到新程序目录即可。
> 启动时如果检测到旧配置，状态栏会提示一句，路径同上。
>
> **打包目录固定为 `dist`**（v2.01.21 起）：以后新版本直接覆盖
> `dist\MonitorBrightness.exe`，配置与日志原地保留，不用再拷配置。

**遇到问题想让我快速定位？** 程序会往**自己所在目录**写一份诊断日志
`diag.log`（JSON Lines），把"当时读到了什么、算了什么、提交了什么、
Windows 返回了什么"原样记下来。装在 Program Files 这类不可写的位置时，
日志会自动改放 `%APPDATA%\MonitorBrightness`（`--diag` 里会写明是哪种）。
- 看内容：设置 → 关于 →「打开日志目录」，或命令行 `--diag-log`。
- **要发给别人**：设置 → 关于 →「导出诊断包」，会把日志 + 配置打成一个
  zip 放在程序目录；命令行等价物是 `--diag-export`。
- 不想要它：设置 → 关于 → 把「诊断日志」关掉（关掉后立刻停止写入）。
- 这是**临时模块**，等这个软件稳定了会整体删掉。

**为什么「检测」有时只显示"状态未知"？**因为 Windows 没有可靠的"显示器电源"读取接口。读得到的只有两种硬信号：
拓扑里这条 path 是否 ACTIVE（拓扑模式），以及 DDC 的 `0xD6` 电源寄存器。
但本机实测 `0xD6` **会撒谎**——面板已经黑了它仍报 `1`（v1.5.0 的"程序说亮着、
屏幕其实黑着"就是这么来的）。所以程序只采信它可信的那个方向：
**报 2/3/4/5 才算灭**，报 `1` 时一律显示"状态未知"，把寄存器值和
"上次键鼠输入距今多久"一起摊给你自己判断。用「拓扑断开」方式时没有这个问题——
拓扑的 ACTIVE 就是系统事实，结论是准的。

> 顺带排除一个思路：有人会想到"盖一个全屏黑窗"。它在远程下不成立 ——
> 黑窗同样会出现在远程画面里，等于把远程也蒙住。

**动鼠标会把屏幕弄亮吗？会。** 系统级熄灭等价于 Windows 自己的"关闭显示器"

### DDC 待机的风险（必须说明）

1. 微软 `SetVCPFeature` 文档原话：*"Many monitors don't fully implement that standard;
   so your use of these commands might result in undefined monitor behavior."*
2. ddcutil 文档：DDC/CI 只在 I²C 层确认"包收到了"，**不确认显示器真的执行了**；
   "关闭"还可能让显示器把 DDC 通道一起断掉，此后再发"开机"就没有可靠路径。
3. 社区里"DDC 关机后显示器变砖"的报告集中在 `0xD6=4/5`（Twinkle Tray #1213 / #432）。

本机实测能力串是 `D6(01 04 05)` —— 只声明 开(1) / 软关(4) / 硬关(5)，
**没有声明待机(2)**。所以程序默认会跳过未声明的值；你在下拉里主动选
「DDC 单屏待机」时会弹一次风险确认，确认后才允许强制写入。

### 点亮：快速路径与唤醒阶梯

v1.9.7 起，点亮默认先走**快速路径**（`0x60` 切源翻转）：

- 读 `0x60` 当前输入源 → 写一个**不同**的中间源 → **立即**写回原源。DP 接收端靠
  "离开当前口再回来"重新做链路训练，所以中途不需要等待；实测 3 次 DDC 事务约 **180ms**。
- **逐台**翻转：同时勾选多台也是各自翻转，**不发** `SC_MONITORPOWER` 广播。
- 只在「熄灭方式 = DDC + 允许切信号源 + 记账认为刚才熄过屏」时启用；其它情况照旧走完整阶梯。
- 同一台 **8 秒内第二次点亮**自动升级为完整阶梯（事件日志写「已升级为完整点亮」）。
- 翻转失败（读不到源 / 写不进 / 写回后源没变）立即回退完整阶梯，并写明原因。
- 想完全回到 v1.9.6 的旧行为：退出程序，编辑 `config.json` 把 `"wake_fast_flip"` 改成 `false`
  （旧配置没有这个键时按 `true` 处理）。

**唤醒阶梯**（逐级加码）：

1. `0xD6=1` 电源模式 → 开
2. 写回当前亮度（部分固件靠收到 VCP 写入才醒）
3. **输出重驱动**：`SC_MONITORPOWER 2 → -1`，强制 GPU 与面板重新握手
   （"亮着却黑屏"在公开排查里都归因为握手失败，标准恢复手段就是这一步）
4. 切信号源（DP+HDMI 双线时可能切到空口，配置 `wake_switch_input=false` 可关）

另外两个能提高成功率的动作：把显示器 OSD 里的 **Deep Sleep / Eco / 超省电**关掉；
出问题先跑 `--diag`，里面有每个输出的 `0xD6/0x60/0x10` 回读和能力串支持值。
诊断报告另有一段"显示拓扑（只读）"：列出每块屏的 `ACTIVE` / 稳定锚点 / GDI 名 / 同源别名，
能直接看出哪块屏是被断开的、哪块只是线没插——这段不需要点亮屏幕，排障时很安全。

## 备选方案（纯命令行）

若不想装本程序，可用 NirSoft **ControlMyMonitor** 走同样的 DDC/CI：

```bat
ControlMyMonitor.exe /SetValue Primary 10 80
```

配合 Windows「任务计划程序」定时调用即可（记得在任务属性里勾上
「如果错过计划开始时间，请尽快启动任务」，这是本工具 v1.1.0 自动帮你做的事）。
